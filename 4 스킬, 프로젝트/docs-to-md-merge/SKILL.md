# PDF·한글·TXT → MD 변환·정규화

케니님이 반복하는 작업: PDF, 한글(HWP/HWPX), TXT 파일을 MD 파일로 변환하고 AI가 읽고 처리하기 좋은 형태로 정리(정규화)한다. 파일이 하나이든 여러 개이든 동일하게 적용한다 — 형식별 변환과 정규화 로직은 파일 개수와 무관하게 동일하고, 다른 건 병합 순서와 출처 표시 단계뿐이다. 실제 방송심의 규정·해설집·지침·의결사례 파일로 테스트를 거쳐 확정한 절차다.

## 전체 절차

1. 대상 파일을 확장자별로 분류한다 (PDF / HWP·HWPX / TXT).
2. 각 파일에서 텍스트를 추출한다 (아래 '형식별 변환 방법' 참조).
3. 추출된 텍스트를 정규화한다 (아래 '정규화 규칙' 참조). 이 단계까지는 파일 개수와 무관하게 동일하게 적용한다.
4. **파일이 1개만 있으면** 정규화된 본문을 그대로 하나의 MD 파일로 저장하고 6번으로 간다 (아래 5·6번은 생략). **파일이 2개 이상이면** 문서 성격(규정 → 해설·지침 → 개별 사례처럼 문서의 위계와 성격)을 판단해서 병합 순서를 정한다. 파일명에 회차·연도·날짜 등 순서 정보가 뚜렷하면 그 순서를 우선하고, 그 경우 회차나 연도의 공백·중복이 있는지 검증해서 발견되면 본문 중 해당 위치나 대화로 알린다.
5. (파일이 2개 이상일 때만) 각 원본마다 `## 제목` 아래에 `*(원본: 파일명)*` 형태로 출처를 표시해 구분한다.
6. 최종 결과는 하나의 MD 파일로 저장한다. 파일 맨 위에 별도 요약 블록은 넣지 않는다 — 본문만 깔끔하게 담고, 발견된 이슈나 확인이 필요한 사항은 대화로 보고한다.

## 형식별 변환 방법

**원본 우선:** 같은 문서의 HWP·HWPX 원본이 있으면 PDF가 아니라 원본을 변환한다. PDF는 글자 좌표만 남아 문단 끊김·표 분리·세로 글자 쪼개짐이 생기기 때문이다(2026-11-20 점검: ezPDF·한컴 PDF의 글자 깨짐은 0에 가까웠으나, 2026년 소위 회의자료 PDF의 표 밖 본문 줄 약 48%가 문장 중간에서 끊김). 사용자가 HWP를 준 경우 PDF로 바꿔 달라고 하지 않는다. 배포용·암호·DRM 문서이거나 kordoc이 실패할 때만 PDF를 요청한다.

기본 도구는 **kordoc**이다. HWP·HWPX와 표가 있는 PDF에서 표(rowspan·colspan 포함)를 보존하고 열이 뒤섞이지 않기 때문이다. (2026-10-29 비교 테스트: pyhwp는 별표·별지 표 7개를 "<표>"로만 출력해 내용이 사라졌고, pdftotext는 표 열이 섞여 민원 요지와 검토의견이 뒤엉켰다.)

- **HWP·HWPX**: 표 유무와 관계없이 항상 kordoc으로 변환한다. kordoc 실행이 실패하거나 빈 결과를 내면 HWP는 `pyhwp`의 `hwp5txt`로, HWPX는 zip을 풀어 XML을 직접 파싱하는 방식으로 대체하고, 대체했다는 사실과 표가 누락됐을 수 있음을 대화로 보고한다. pyhwp는 일반 `pip install pyhwp`로 설치되는 경우가 많고, 빌드 충돌이 나면 그때 `setuptools==59.6.0`과 `six`를 넣은 구버전 setuptools 가상환경을 쓴다. 배포용·암호 문서는 보안 정책을 우회하는 처리를 하지 않으며, kordoc으로 읽을 수 있더라도 사용 여부를 사용자에게 먼저 확인한다.
- **PDF**: kordoc과 `pdftotext -enc UTF-8`(raw 모드, `-layout` 금지)로 둘 다 변환한다. `-enc UTF-8`은 필수다(이 PC에서 옵션 없이 실행하면 한글이 0자로 출력됨). kordoc 출력의 표 개수(아래 '표 개수 세는 법')가 1개 이상이면 kordoc 결과를 채택한다. 0개이면 텍스트 위주 PDF로 보고 pdftotext 결과와 비교해 더 나은 쪽을 쓴다(kordoc은 느림: 562쪽 기준 25초 대 2초). kordoc 실행이 실패하면 `pdftotext` 결과로 대체하고, 대체했다는 사실을 대화로 보고한다. 스캔본이라 텍스트 레이어가 없으면 OCR이 필요하다는 점을 밝히고 임의로 내용을 지어내지 않는다.
- **kordoc 호출 방법**: CLI로 호출한다(MCP 아님). 처음 실행하기 전에 `node -v`로 Node 버전이 20 이상인지 확인한다. Windows에서는 처음 실행할 때 npx가 패키지를 내려받으므로 시간이 걸린다.

  ```
  npx -y kordoc@4.25.2 <입력파일> -o <출력.md>
  ```

  **판 고정:** 판 번호 없이 `npx -y kordoc`을 쓰면 실행할 때마다 최신판을 받아 출력이 몰래 바뀐다(2026-11-20 확인: 4.24.17→4.25.2에서 같은 PDF의 표 인식이 39개→27개로 줄고 끊긴 줄이 약 16% 늘었음, 본문 글자는 같음). 항상 판 번호를 붙여 실행하고, 판을 올릴 때는 기존 변환본 1~2개를 새 판으로 다시 변환해 비교한 뒤 이 문서의 판 번호를 고친다.

  **쪽 주석이 필요할 때(PDF):** kordoc 출력에는 쪽 구분이 없다. 쪽 주석(`<!-- p.N -->`)이 필요하면 `-p N --no-images --plain`으로 쪽마다 변환해 이어 붙인다(쪽당 약 1초). 이 경우 쪽 바닥글이 지워지므로 한글 음절 수를 pdftotext와 비교해 차이가 바닥글뿐인지 확인한다.

  (검증 환경: kordoc 4.24.17. 2026-10-29 클라우드(리눅스)에서 HWP·PDF, Windows 11·Node 24.19.0에서 HWP·HWPX·PDF 변환 검증(한글 음절 수 기준 비교, 표의 행·열 배치는 육안 대조 전).) 그림은 출력 MD와 같은 폴더의 `images/<출력파일명>/` 하위에 `manifest.json`과 함께 저장된다.
- **표 개수 세는 법** (PDF에만 적용. HWP·HWPX에는 쓰지 않는다): kordoc 출력의 표는 두 형식이다. 단순 표는 GFM 형식(행 시작 `| `, 구분선 `| --- |`), 병합 셀이 있는 표는 HTML `<table>`(rowspan·colspan 포함)이다. 표 개수 = `| --- |`로 시작하는 구분선 수 + `<table>` 수.
- **TXT**: 인코딩(UTF-8/CP949 등)을 확인한 뒤 그대로 사용한다.

### kordoc 출력 후처리

- 제목 수준(#, ##, ###)이 문서마다 들쭉날쭉할 수 있다(조문 일부만 ### 제목이 되거나, 문서 제목과 항목 제목의 수준이 뒤집힘). 임의로 고쳐 쓰지 않고 그대로 두되, 심한 경우 대화로 알린다.
- 빈 서식 표(평가표 등)의 빈 행이 수십 줄 남을 수 있다. 내용이 전혀 없는 행이 연속될 때만 제거하고, 제거했음을 대화로 알린다.
- 쪽을 넘는 표 칸이 분리된 경우(테스트에서 4건)가 있으면 알린다.

## PDF 정규화 규칙

아래 규칙은 **pdftotext로 변환한 PDF에만** 적용한다. kordoc 출력(HWP·HWPX, 표가 있는 PDF)에는 문단 재조립 규칙을 적용하지 않는다. 다만 반복 머리말/꼬리말 제거와 양쪽정렬 공백 안내는 kordoc으로 변환한 PDF에도 필요한지 확인한다. 반복되는 표 머리글은 표 구조의 일부이므로 제거하지 않는다.

- 페이지마다 반복되는 머리말/꼬리말(예: 문서 제목, "법제처 / 페이지번호 / 국가법령정보센터" 같은 3줄짜리 꼬리말)은 줄 사이에 빈 줄이 끼어 있어도 통째로 찾아 제거한다. 페이지 끝에서 꼬리말이 정확히 어디 위치할지는 PDF마다 다르므로, 고정된 위치가 아니라 패턴 매칭으로 찾는다.
- 줄바꿈으로 끊긴 문장은 하나의 문단으로 재조립한다. 판단 기준: 다음 줄이 조항 번호(제N조/항/호), 원 문자(①②③), 숫자+마침표, 가나다 항목, 붙임/별표/별지/부칙 같은 '새 항목 시작' 패턴이면 새 문단으로 끊고, 그렇지 않고 현재까지 모은 텍스트가 아직 문장 종결 부호(다./함./음./>. 등)로 끝나지 않았다면 이어 붙인다. 빈 줄 자체는 PDF 줄바꿈의 잔재이므로 구조 신호로 쓰지 않는다.
- 옆면에 세로로 인쇄된 절(節) 색인 탭처럼 장식 요소가 있는 편람형 PDF(예: 해설집류)는, 한 글자짜리 줄(장식 텍스트 조각)만 걸러내는 선에서 정리한다. "제1 절"처럼 두 글자 이상 붙어 나오는 잔재까지 완전히 제거하려면 PyMuPDF 같은 좌표 기반 도구가 필요하지만, 테스트 결과 이 정도 잔재는 AI의 문서 이해에 실질적 영향을 주지 않으므로 기본적으로는 도입하지 않는다. (나중에 특정 문서에서 검색·요약 품질 문제가 실제로 확인되면 그때 개별적으로 좌표 기반 필터링을 검토한다.)
- 양쪽정렬(justify) 조판 때문에 줄바꿈 지점에서 단어 중간에 공백이 남는 경우(예: "왜곡하 여")가 있을 수 있다. 이건 자동으로 완전히 교정하기 어려운 유형의 오류이므로, 결과물에 이런 흔적이 남을 수 있다는 점을 밝히고 필요하면 사람이 훑어보도록 안내한다.

## 절대 하지 않는 것

- 원문에 없는 내용을 추론해서 채우거나, 불확실한 추출 결과를 임의로 고쳐 쓰지 않는다.
- 파일명만으로 알 수 없는 정보(사건명, 의결번호 등)를 임의로 지어내지 않는다 — "확인필요"로 표시한다.
- 텍스트 레이어가 없는 스캔본을 OCR 없이 임의로 옮겨 적지 않는다.
