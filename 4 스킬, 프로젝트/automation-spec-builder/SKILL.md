# 업무 자동화 계획 (Automation Spec Builder)

사용자가 말로 설명한 반복 업무를 **실제로 개발할 수 있는 계획**으로 바꾸고, 사용자가 원하면 그 계획대로 **도구를 실제로 만들어 시험까지** 한다.

| 단계 | 언제 | 따를 내용 |
|---|---|---|
| 계획 | 업무 설명을 받았을 때 | 아래 0~9단계 |
| 제작 | 계획을 확인한 사용자가 제작을 요청했을 때 | `references/제작절차.md` (B0~B8) |
| 이어가기 | 이전 세션의 제작을 이어갈 때 | 설계 폴더의 `05_제작기록.md`부터 읽는다 |

계획 단계의 결과물은 아래 4개다. 사용자가 원하면 한 파일로 합친다.

1. 업무 자동화 브리프 (문제·AS-IS·TO-BE·범위)
2. 기술 타당성 및 외부 연동 검증(Smoke Test) 계획
3. 상세 기술설계서 — `references/기술설계서_템플릿.md` 구조를 따른다
4. 설치·실행 인수 테스트

실제 대화로 설계안을 만든 사례는 `references/사례_방송심의안건.md`에 있다. 질문 순서와 결정 방식은 이 사례를 참고한다.

## 작업 순서

### 0단계. 이미 있는 도구부터 확인

새로 설계하기 전에 같은 일을 하는 도구가 이미 있는지 본다. 있으면 "새로 만들기"가 아니라 "기존 도구 확장"으로 계획한다.

- `J:\AI 자료\4 스킬, 프로젝트\_스킬_카탈로그.md`와 그 폴더의 도구 폴더들
- `C:\Users\user\.claude\skills\` 아래 스킬
- 확인한 결과(재사용할 것·겹치는 것)는 브리프의 "기존 자산" 항목에 적는다.
- **사용자가 이미 가진 계획 자료**(다른 AI와의 대화, 업무지시서, 메모)가 있는지 묻고, 있으면 먼저 읽는다. 열 제목·양식 항목 같은 확정 정보는 가져오고, 전제가 다른 곳(실행 형태, 로컬 AI, 보안, AI 판단 범위)은 표로 보여 주고 어느 쪽으로 갈지 사용자에게 정하게 한다.
- **시험 실행:** 사용자가 "기존 도구는 무시하고 시험" 같이 조건을 주면 이 단계를 건너뛰고, 브리프 첫머리에 그 조건을 `[사용자 확인]`으로 적는다.

### 1단계. 업무 문제 정의

사용자 설명에서 다음을 뽑는다. 없는 항목은 비워 두고 2단계에서 묻는다.

```text
업무명 / 목적
현재 업무 흐름과 반복 주기
입력 자료(형식·출처·양)
현재 결과물(형식)
수작업 병목, 오류·누락 가능성
원하는 최종 결과
사람이 반드시 판단해야 하는 지점
```

### 2단계. 꼭 필요한 것만 묻기

- 구현 방식이 완전히 달라지는 정보만 묻는다. 한 번에 3개 이하, AskUserQuestion으로 선택지를 준다.
- 결과에 큰 영향이 없는 정보는 기본안을 정하고 `[가정]`으로 표시한다.
- 외부 API·인증·데이터 구조처럼 틀리면 구현이 실패하는 정보는 추측하지 않고 `[TODO]`로 둔다.

**반드시 먼저 확정할 것(이것을 모르면 기술을 추천하지 않는다):**

| 질문 | 왜 먼저인가 |
|---|---|
| 최종 결과물 형식(HWP·HWPX·엑셀·PDF·화면 등) | 문서 라이브러리와 저장 방식이 갈린다. 예: HWP 출력이면 python-docx가 아니라 한글 COM·HWPX 처리 |
| 실행 환경(OS·RAM·GPU·설치 프로그램·인터넷 가능 여부) | 로컬 AI 가능 범위와 배포 방식이 갈린다 |
| 입력 자료의 실제 형식과 견본 | 견본 없이 필드명·양식 매핑을 만들지 않는다. 파일이 없으면 **구조 정보만이라도**(엑셀 열 제목, 양식의 항목 이름) 받는다 |
| 자료의 외부 전송 가능 여부(보안등급) | 외부 AI API 사용 여부가 갈린다 |
| 사람이 정할 것과 자동화할 것의 경계 | 판단 업무에서 AI가 어디까지 하는지(후보 제시 / 초안 작성 / 판단)에 따라 구조가 갈린다. 선택지에 "사람이 정해서 입력"을 꼭 넣는다 |

- 질문 선택지는 한쪽 답으로 몰지 않는다. 자동화 범위를 물을 때는 "자동화하지 않음(사람이 함)"도 선택지로 준다.
- 견본 파일이 없으면 브리프에서 "견본 없이 상세 설계를 쓰면 ○○ 부분이 TODO로 남는다"고 알리고, 견본을 기다릴지 먼저 진행할지 묻는다.
- 외부 전송이 제한되면 표준 통제를 설계에 넣는다: 외부 AI 사용은 기본 꺼짐, 보낼 항목 선택·내용 미리보기·제공업체와 모델 표시·담당자 승인, 전송 기록(일시·모델·자료 종류·작업 번호·결과), API 키는 Windows 자격 증명 관리자에 저장.

### 3단계. 실행 형태 결정

아래 셋 중 하나를 근거와 함께 추천하고 사용자 결정을 받는다.

| 기준 | Claude 스킬(대화 안에서 실행) | 독립 프로그램 | 하이브리드 |
|---|---|---|---|
| 초기 구축 | 빠름 | 느림 | 중간 |
| 대량·반복 처리, 예약 실행 | 약함 | 강함 | 스크립트가 맡음 |
| AI 모델 선택·로컬 AI | 고정 | 자유 | 단계별로 다르게 |
| 판단·문장 작성 품질 | 강함 | 쓰는 모델에 따라 다름 | 판단은 Claude |
| 이력·DB 관리 | 약함 | 강함 | 스크립트가 맡음 |

- 기본 추천은 **하이브리드**다: 무거운 기계 작업(전사·변환·수집·정리)은 Python 스크립트, 판단·작성은 Claude 스킬이 맡는다. 이 PC의 기존 도구(video_to_draft.py, hwp_to_pdf.py 등)가 이 구조다.
- 독립 프로그램은 "AI를 거치지 않고 버튼으로 반복 실행"이나 "여러 사람이 사용"이 필요할 때 추천한다.
- AI 모델을 바꿔 쓸 필요가 있으면 작업 단계별로 모델을 지정하는 Adapter 구조를 넣는다(전사=로컬, 분류=로컬 소형, 판단·작성=상용 API, 검수=다른 모델).

### 4단계. AS-IS → TO-BE

- AS-IS: 사람이 지금 하는 순서를 단계별로 쓰고, 단계마다 `자동화 가능 / 규칙으로 가능 / AI 보조 유용 / 사람 판단 유지`를 표시한다.
- TO-BE 원칙:
  - 규칙으로 풀리는 일에 LLM을 쓰지 않는다.
  - 수집·저장·AI 처리를 분리한다. AI 실패가 원본 저장을 막지 않는다.
  - 바뀌지 않은 자료는 다시 처리하지 않는다(해시로 변경 감지).
  - 큰 자료(영상·긴 문서)는 통째로 AI에 넣지 않는다. 전사·검색으로 필요한 구간만 넘긴다.
  - **AI는 초안·후보를 만들고 사람이 결정한다.** 판단 업무에서는 결과를 `가능성 높음 / 추가 검토 / 가능성 낮음`처럼 나누고, 과거 사례 결론을 정답처럼 복사하지 않는다.
  - **사람이 고친 결과가 다음 단계의 입력이 된다.** 자동 결과(전사·추출·초안)는 사람이 고칠 수 있게 수정본 파일을 따로 두고, 다시 실행해도 수정본을 지우지 않으며, 고친 이력을 남긴다.
  - **오래 걸리는 작업은 나눠서 중간 저장하고, 실패하면 이어서 처리한다.**

### 5단계. 자료 저장 형식 정하기

| 자료 성격 | 권장 형식 | 원칙 |
|---|---|---|
| 표 형태 기록(의결 내역·목록) | 원본 xlsx 보존 + 변환 CSV(또는 SQLite) | 원본 열은 그대로 두고, 검색용 내부 필드(분리값·정규화값)는 따로 만든다. AI가 만든 요약·분류 필드는 이름으로 구분한다(예: `ai_` 접두어). 식별자 규칙(공식 번호 우선, 없거나 중복이면 내부 번호)과 인코딩(UTF-8·BOM·CP949)·열 이름 매핑을 정한다. 결론과 이유는 다른 필드로 나눈다 |
| 규정·지침 문서 | 조항별 MD + front matter(조항번호·시행일·버전) + 개정 이력·조 번호 대응표 | 원문과 AI가 쓴 해석을 섞지 않는다. **판단 대상 시점의 판**으로 조회하고, 과거 사례 당시 조항과 현재 조항을 구분해 적는다 |
| 출력 양식 | 유형별 템플릿 여러 개 + 매핑 설정(JSON) | 양식마다 입력 위치를 정의하고, 양식 선택은 추천하되 사람이 정한다 |
| 신규 자료 추가 | 갱신 절차(읽기→변환→중복 확인→추가→색인 갱신→변경 기록) | 추가할 때마다 코드를 고치지 않는다. **프로그램 갱신과 자료 갱신을 분리**한다(코드와 `data\`를 나눔) |

### 6단계. 기술 타당성과 Smoke Test 계획

- 공식 API 여부, 로그인 필요 여부, 호출 제한, 갱신 주기, 이용약관, 로컬 실행 가능성을 표로 정리한다.
- **로컬 환경은 명령으로 직접 확인한다**(읽기 전용 점검: Python·패키지 버전, 외부 프로그램 PATH, 한글 COM 실행·종료 등). 확인한 것은 `[검증 완료]`와 날짜로 적는다. 설치·설정 변경은 하지 않는다.
- 핵심 외부 연동마다 실제 요청 1건으로 확인할 항목(URL·파라미터·응답·식별자·페이징·인증·오류 응답)을 계획한다.
- 사용자가 허용하면 공식 문서 확인이나 실제 1건 시험을 직접 해서 `[검증 완료]`로 바꾼다. 하지 않은 것은 `[TODO]` 그대로 둔다.
- 로컬 AI·음성인식 성능은 "사양상 가능"과 "이 PC에서 측정함"을 구분한다. 측정 전에는 후보와 시험 방법만 쓴다(예: 실제 사례 10~20건으로 품질 비교).

### 7단계. 범위와 우선순위

- P0 핵심 / P1 1차 완성 / P2 편의 / P3 확장으로 나누고 `1차 개발 제외`를 명시한다.
- 개발 단계는 "기본 동작 → 판단·분석 → 문서 출력 → 고도화" 순서로 잘게 나눈다.

### 8단계. 상세 기술설계서 작성

`references/기술설계서_템플릿.md`의 절 번호와 구조를 따른다.
- 해당 없는 절은 지우지 말고 `해당 없음(이유)` 한 줄로 둔다. 해당 없는 절이 이어지면 한 줄에 묶는다(예: "29·41절 해당 없음 — 수집형 아님").
- 템플릿은 웹앱·수집형 기준이다. 실행 형태별로 이렇게 바꿔 쓴다.

  | 실행 형태 | 바꿔 쓸 절 |
  |---|---|
  | 웹앱·수집형 | 템플릿 그대로 |
  | 스크립트 + Claude 스킬 | 24~28절 → 실행 명령표·대화 흐름, 16절 → 파일 관리(DB 없으면), 20절 → 해당 없음 또는 "입력 묶음 파일로 다른 AI에 넘길 수 있게" |
  | 독립 GUI 프로그램 | 24~27절 → 화면별 기능, 28절 → 화면 구성, 44절 → 배포(PyInstaller 등) |
- 50절(미확정 TODO)에 모든 `[TODO]`를 모은다.
- 53절(개발용 AI 지시)에 다음을 반드시 넣는다: 확인 안 된 API 필드를 만들지 않는다 / 외부 연동 검증 후 개발 / Adapter로 외부 종속 격리 / AI 오류가 원본 저장을 막지 않음 / 실제 사용자 실행 시나리오 검증 / 시험하지 않은 것을 완료라고 쓰지 않음.

### 9단계. 인수 테스트

최소: 첫 설치, 정상 실행, 핵심 업무 1회, 재실행·데이터 유지, 잘못된 인증키, 네트워크 오류, AI 실패.
Windows 로컬 도구면 추가: 실행 파일(.bat/.cmd) CRLF, CMD 인코딩, 한글 경로, Python 탐지, 가상환경, 설치 실패 처리, 오류 시 창 유지.

## 출력 모드

| 모드 | 언제 | 내용 |
|---|---|---|
| Quick | 아이디어 검토만 원할 때 | 업무 문제, 자동화 가능 범위, 추천 실행 형태, 핵심 위험, 다음 단계 — 채팅으로 답한다 |
| Standard(기본) | 계획서를 원할 때 | 브리프, 타당성, 상세 설계서, Smoke Test 계획, 인수 테스트 |
| Deep | 개발 착수 직전·복잡한 시스템 | Standard + 상세 DB 스키마, API, 데이터 흐름, 예외 시나리오, 보안·개인정보, 비용·호출량, Migration, 유지보수, 세부 테스트 케이스 |

선택 결과물 — **요약 업무지시서**: 사용자가 원하거나 다른 사람(개발자·다른 AI)에게 넘길 때, 상세 설계서를 2~3쪽으로 줄인 `00_업무지시서.md`를 만든다. 목적, 확정 전제, 기능 목록(P0~P2), 자료 구조, 지켜야 할 원칙, 검수 기준, 추후 제공 자료만 담고, 상세는 03 문서를 가리킨다.

Standard·Deep은 바로 전체를 쓰지 않는다. **브리프(1단계~5단계 요약)를 먼저 보여 주고 사용자 확인을 받은 뒤** 상세 설계서를 쓴다.

## 정보 상태 표기

```text
[사용자 확인] 사용자가 직접 말한 내용
[검증 완료]   실제 문서·API·시험으로 확인한 내용
[설계 제안]   설계자가 고른 구현안
[가정]        사용자 확인 전 임시 전제
[TODO]        구현 전 확인 필요
[확인 불가]   현재 자료로 판단할 수 없음
```

추론을 사실처럼 쓰지 않는다. 도구·모델·라이브러리의 성능이나 지원 여부를 단정하려면 확인 근거가 있어야 한다.

## 제작 단계 (요약 — 자세한 내용은 `references/제작절차.md`)

계획서를 사용자가 확인한 뒤 제작을 요청하면 시작한다. 한 번에 전체 코드를 쓰지 않는다.

```text
B0 착수 조건 확인(P0 확정, P0를 막는 TODO 없음)
B1 작업 나누기 + 05_제작기록.md
B2 도구 폴더 만들기: J:\AI 자료\4 스킬, 프로젝트\<도구명>\ (J 루트 금지)
B3 외부 연동 Smoke Test 실제 실행(연동이 없으면 건너뜀)
B4 작업별 구현 → 견본으로 실행 → 결과 직접 확인 → 기록
B5 P0 끝나면 실제 자료 1건으로 시연, 사용자 확인
B6 P1 이후 반복
B7 인수 테스트 실제 실행(PASS/FAIL/미실시)
B8 README·CHANGELOG, 스킬이면 정본+사본, 카탈로그 갱신, 메모리 기록, 완료 보고
```

설치, 기존 도구 수정, 유료 API 호출, 외부 전송, 시스템 설정, 삭제, 커밋은 승인을 받고 한다(목록은 제작절차.md 끝). 시험하지 않은 것은 완료라고 쓰지 않는다.
